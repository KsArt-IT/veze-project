# PRD — «Везе. Сама.»

> Сама везе — куди скажеш, довезе.

Веб-приложение для заказа беспилотного такси. Водителя нет: пассажир заказывает поездку,
система назначает свободную автономную машину, машина сама приезжает, открывается по коду
и везёт по маршруту. Человек в контуре есть только на стороне оператора (удалённая помощь).

**Главное решение:** на первом этапе это игра — реальных машин нет, их эмулирует сервер.
Всё остальное (пассажир, оператор, админ, оплата, БД, API) делается как для реальной
эксплуатации. Эмулятор подключается через тот же интерфейс, что и будущий парк реальных машин,
поэтому переход — это замена адаптера, а не переписывание приложения.

Статус документа: черновик v0.1 (2026-09-26). Цель — зафиксировать рамки MVP, а не описать всё.

---

## 1. Роли

| Роль | Кто это | Что делает |
|---|---|---|
| Пассажир (`rider`) | Клиент | Заказывает, отслеживает, оплачивает, оценивает поездку |
| Оператор (`operator`) | Сотрудник диспетчерской | Следит за парком, реагирует на инциденты, помогает пассажиру удалённо |
| Техник (`technician`) | Сотрудник депо | Обслуживание и зарядка машин в своём депо |
| Админ (`admin`) | Владелец сервиса | Тарифы, промокоды, машины, пользователи, отчёты |

Авторизация общая для всех ролей: один аккаунт (`users`), способы входа — телефон (OTP или пароль),
email, Google, Apple; их у аккаунта может быть несколько, все ведут в один профиль. Один человек может
быть и пассажиром, и сотрудником. У сотрудника роль одна. Общий профиль на семью — не в MVP.

Роли `driver` нет — вместо водителя «исполнитель» поездки это машина (`vehicle`).

## 2. MVP — что входит

### Пассажир
1. Регистрация / вход по телефону (OTP или пароль), email, Google или Apple.
2. Выбор точки подачи и назначения на карте или по адресу.
3. Расчёт стоимости и времени до заказа (по классу авто: economy / comfort / business).
4. Заказ поездки → назначение ближайшей свободной машины.
5. Отслеживание машины на карте в реальном времени (подача и поездка).
6. Посадка: машина открывается по PIN-коду из приложения (или кнопкой «Открыть»).
7. Отмена поездки (бесплатно до назначения, дальше — по правилам тарифа).
8. Оплата: карта (эмуляция платёжного шлюза в MVP), промокод.
9. Оценка поездки 1–5 + комментарий и теги причин; оценка помощи оператора после инцидента.
10. История поездок.
11. Кнопка «Нужна помощь» во время поездки → связь с оператором.

### Оператор
1. Карта парка: все машины, их статус, заряд, текущая поездка.
2. Лента инцидентов (помощь пассажиру, остановка машины, ошибка датчиков).
3. Действия: остановить машину, отправить на базу, завершить/отменить поездку.

### Админ
1. CRUD машин, тарифов, промокодов.
2. Простые отчёты: поездки и выручка за период, средний рейтинг, загрузка парка.

### Эмулятор машин (игровой парк)
Реальных беспилотников нет, поэтому сервер содержит **эмулятор**: двигает машины по маршруту,
шлёт координаты, меняет заряд, иногда генерирует инцидент.

Правила, чтобы эмулятор потом заменился на реальные машины без переделок:
- Приложение общается с машиной только через интерфейс `VehicleGateway`
  (команды: ехать к точке, открыть двери, остановиться, на базу; события: позиция, статус,
  заряд, инцидент). Реализации: `SimulatedVehicleGateway` сейчас, реальная — потом.
- Ядро (заказ, назначение, цена, статусы, оплата) не знает, эмулирована машина или нет.
- В БД машины одинаковые; признак источника — `vehicles.source` (`simulated` / `real`),
  используется только для выбора адаптера.
- Эмулятор — отдельный модуль/процесс, его можно выключить конфигом.

## 3. Вне MVP (позже)

- Мобильное приложение (React Native / Flutter).
- Совместные поездки (несколько пассажиров, попутчики).
- Предзаказ на время.
- Реальный платёжный провайдер (LiqPay / Stripe / Fondy).
- Динамическое ценообразование (surge).
- Зоны обслуживания (геозоны), где разрешена работа беспилотника.
- Мультиязычность (uk / en) — заложить в архитектуру, но в MVP только uk.

## 4. Жизненный цикл поездки

```
requested ─► assigned ─► en_route ─► arrived ─► in_progress ─► completed
    │            │           │          │             │
    └────────────┴───────────┴──────────┴─────────────┴──► cancelled
                                                       └──► incident ─► completed | cancelled
```

| Статус | Смысл |
|---|---|
| `requested` | Пассажир создал заказ, машина ещё не назначена |
| `assigned` | Система закрепила машину |
| `en_route` | Машина едет к точке подачи |
| `arrived` | Машина на месте, ждёт посадки (таймер ожидания, после — платное ожидание / отмена) |
| `in_progress` | Пассажир сел (PIN подтверждён), едем |
| `completed` | Доехали, рассчитана итоговая цена |
| `cancelled` | Отменено пассажиром, оператором или системой (с причиной) |
| `incident` | Нештатная ситуация, поездкой управляет оператор |

## 5. Ключевые бизнес-правила

- Цена = `max(min_fare, base_fare + km × price_per_km + min × price_per_min) × (1 − промо%)`.
- У пассажира одновременно не более одной активной поездки.
- Посадка и высадка только на `pickup_points` (подробности и следствия для данных — в разделе 6).
- Машина в поездке не может быть назначена на другую.
- Машина с зарядом ниже порога (напр. 20 %) не назначается и уходит на зарядку.
- Одна оплата на поездку; одна оценка от пассажира на поездку.
- Все деньги — `DECIMAL(10,2)`, валюта `UAH`.

## 6. Данные (черновик сущностей)

Уже есть — адреса и навигация: `countries`, `cities`, `streets`, `buildings`, `road_nodes`,
`road_segments`, `pickup_points`, `depots`, `service_zones`; авторизация — `users`,
`user_identities`, `user_sessions`, `auth_codes`; профили — `passengers`, `employees`;
у пассажира — `saved_locations`, `payment_methods`.

Дальше: `vehicle_classes` (тарифы), `vehicles`, `rides`, `ride_events`
(история смены статусов и трек), `payments`, `promo_codes`, `ratings`, `incidents`.

Ключевые решения:
- таблицы `drivers` нет — статус, заряд, координаты и признак «на линии» хранятся в `vehicles`;
- `vehicles.status` (`idle`, `busy`, `charging`, `offline`, `maintenance`), `vehicles.battery_level`,
  `vehicles.source` (`simulated`, `real`);
- `rides.vehicle_id` обязателен начиная с `assigned`;
- посадка и высадка — через `pickup_points`, а не произвольные координаты (правило подтверждено
  2026-10-03): беспилотник не может остановиться где угодно, он обязан соблюдать ПДД, в отличие от
  водителя, которому можно сказать «выйду тут». Пассажир может указать любое место (тык в карту,
  «останови здесь»), но сервер подбирает ближайшую активную `pickup_point` внутри активной
  `service_zone`, и машина останавливается на ней. Отсюда:
  - `rides` ссылается на `pickup_points` и для посадки, и для высадки (FK), свободных координат
    в поездке нет; запрошенную точку (`POINT`) добавляем только если понадобится аналитика;
  - «останови на ближайшей» в пути — смена точки высадки на другую `pickup_point`, фиксируется
    в `ride_events`;
  - аварийная остановка не привязана к `pickup_points`: машина встаёт там, где безопасно; это
    событие в `ride_events` с координатой, а не точка высадки;
- `ratings` — только пассажир → поездка (машине оценивать «в ответ» некому). По сути это оценка
  машины и сервиса, поэтому к оценке — теги причин (справочник + связующая таблица): «грязно»,
  «запах», «резкое торможение», «неудобная точка посадки». Низкая оценка с тегом — действие:
  мойка, разбор поведения машины, правка `pickup_points`.
- Рейтинга пассажира нет: ставить ему звёзды некому. Поведение пассажира — факты: инциденты, где
  виновник — пассажир (грязь, повреждения, курение — фиксируют датчики салона или техник), неявки и
  отмены (`rides`), долги (`payments`). Показатель доверия при необходимости считается запросом,
  отдельным полем не хранится; блокировка — `passengers.is_active`.
- Рейтинга оператора нет: пассажир видит оператора только в инциденте. Вместо этого — оценка помощи
  1–5 + комментарий после закрытия инцидента, колонками в `incidents`, без отдельной таблицы.
  Показатели оператора (средняя оценка, время реакции) — запросом по его инцидентам.

Карта таблиц — [architecture/database-tables.md](architecture/database-tables.md).

## 7. Стек

| Слой | Технология |
|---|---|
| Веб (пассажир, оператор, админ) | Next.js (App Router) + React, TypeScript |
| Сервер / API | Node.js + Express (или NestJS), TypeScript, REST + WebSocket |
| БД | MySQL 9.7 LTS в Docker (`veze-node-app`) |
| Карты и маршруты | Leaflet + OpenStreetMap, маршруты — OSRM (бесплатно) |
| Реалтайм | Socket.IO — позиция машины, смена статуса |
| Авторизация | JWT (access + refresh), роли |
| Доступ к БД | Prisma или Drizzle ORM + миграции |
| Валидация | Zod (общие схемы для клиента и сервера) |
| Тесты | Vitest / Jest, Playwright для e2e |
| Инфраструктура | Docker Compose, `.env`, GitHub Actions (lint + test) |

## 8. Нефункциональные требования

- Обновление позиции машины на карте — не реже раза в 2 с.
- Ответ API на типовые запросы < 300 мс.
- Пароли / токены не хранятся в репозитории (`.env` в `.gitignore`).
- Действия оператора и смены статусов логируются (`ride_events`) — для разбора инцидентов.
- Адаптивная вёрстка: пассажирский интерфейс в первую очередь под телефон.
